# ESP32-C3（AI Passport）板卡记录（2026-11-14 更新）

到货设备是 FoloToy AI Passport（ESP32-C3）。这份文档汇总三类信息：**可以复用的真机事实**、**仍未验证的部分**，以及 **MicClicker 相对上一项目新引入、必须补测的项**。

事实来源分三种，正文逐条标明：

- **本轮实测**：2026-11-14 对这台设备做的芯片级探针与整片备份，见第 13 节。这是本文证据等级最高的一类。
- **上一项目实测**：同型号板卡在 `ai-passport-mic` 项目里做过的真机验证（2026-11-06～11-10，commit `7b682ee`，本机 checkout 在 `~/Desktop/github/cnryb/ai-passport-mic`）。
- **BSP / 产品文档**：上游 FoloToy BSP 与官方上手页。

本文只记录实测过的事实与明确未验证项，不替代原理图。

## 1. 结论

- **芯片级已确认（2026-11-14）**：C3 QFN32 rev **v1.1**，封装内 **8 MB XMC Flash**，40 MHz 晶振，MAC `98:c3:77:f6:c6:44`，Secure Boot / Flash 加密均未启用。整片 8 MB 已备份并校验。
- 采集通路、三键、电量计、屏幕、烧录通道都在同型号板上真机验过，**不需要重做整机体检**。
- **MicClicker 本轮新增实测已通过**：Wi-Fi STA 扫描，以及 RELEASED / UP / DOWN / OK 四键态各 400 样本的 ADC 分布与窗口裕量（第 14 节）。
- 但 ESP-NOW 和 G.722 仍未在这颗 C3 上跑过；Wi-Fi 扫描通过不等于 ESP-NOW 链路通过。
- 功耗、独立万用表电压复核仍未确认；绝对电压复核按第 4 节分级为非阻塞项。原理图、硬件版本与咪头型号**已确认上游不公开**（第 2 节），不是待查项。
- **两处需要留意**：①这块板的分区表是 `factory=0x7F0000` 的三项布局，**没有 `cardid` / `recovery`**，与上一项目文档描述的「平台模板」不符（第 13.5 节）；②板上固件停在 `Nov 6 08:32:55` 那版，晚于它的「已验」结论不能直接套用（第 13.4 节）。

## 3. 引脚与外设

引脚事实的唯一来源是上游 BSP（<https://github.com/FoloToy/ai-passport>，MIT；镜像 <https://gitee.com/FoloToy/ai-passport>），文件 `components/bsp/include/bsp_pins.h`，本文件按 commit `55c7519`（2026-11-14）核对。上一项目把它集中写进 `device/main/board.h`，本项目沿用并已与之逐项比对：**全部引脚、总线实例、I2C 地址和电压窗口一致**。

| 外设 | 引脚 / 参数 |
| :--- | :--- |
| LCD（4 线 SPI，SPI2，mode 0，80 MHz） | MOSI=9 / SCLK=8 / CS=1 / DC=20；**RST 未接 MCU**（`-1`，屏复位硬接 3.3V，走 `SWRESET` 软复位） |
| 背光 | GPIO21，LEDC timer0 / channel0 / 10 bit / 5 kHz |
| I2S（全双工） | MCLK=6 / BCLK=5 / WS=3 / DOUT=2 / DIN=4；**功放使能未接 MCU**（`-1`，常通） |
| I2C（codec + 电量计） | SDA=10 / SCL=7，外部 2.2 kΩ 上拉；两器件共用 I2C0，不得另建总线 |
| 按键 | 单 ADC：GPIO0（ADC1 channel 0），电阻梯见第 4 节 |
| 原生 USB | GPIO18/19，保留给控制台与烧录 |
| UART0 | TX=GPIO21，**与背光冲突**，所以控制台必须走 USB-Serial-JTAG |
| NFC | NTAG213 为被动标签，**不占用 GPIO、无 BSP API** |

**GPIO0 是 C3 启动 strapping 管脚**，改这一脚的电路或上拉前必须核对 ESP32-C3 strapping 要求。本板靠外部 10 kΩ 上拉保证启动时的电平。

**按键物理上是 4 颗轻触开关**（板上丝印 `SW1`–`SW4`，沉板处理，受力在板不在焊盘）；BSP 只把其中 3 颗接到 ADC 电阻梯，另一颗是独立的硬件锁存电源键，与 ADC 三键互不相干，MCU 读不到它。

LCD 参考时钟存在**上游内部的表述冲突**：`bsp_pins.h` 的 `BSP_LCD_PCLK_HZ` 与现行硬件开发指南写 80 MHz，但同一仓库另一份文档和 README 写 40 MHz。按时间看是 40→80 的变更。本项目不驱动屏，不影响实现；若日后要用屏，以 `bsp_pins.h` 为准并实测。

## 4. 按键与 ADC 电阻梯

三个功能键共用一个 ADC 引脚，靠分压电阻区分，不是三个独立 GPIO：

```text
3.3V ── 10k 外部上拉 ──┬── ADC(GPIO0)
                       └── 按键 ── 分压电阻 ── GND
```

| 项目 | 值 |
| :--- | :--- |
| 标称电平 | 松开 ≈ 3300 mV / UP ≈ 0 mV / DOWN ≈ 300 mV / OK ≈ 595 mV |
| 判定窗口 | `UP_MAX=150`、`DOWN_MAX=447`、`OK_MAX=1900`（超过即视为松开） |
| 时序 | 消抖 20 ms、双击窗口 180 ms、长按 500 ms。上游在电压解码层另加按键锁：空闲时新窗口须连续稳定 40 ms 才认作按下，锁定后改判须连续稳定 120 ms，用于吸收按住过程中触点短暂断开导致扫过其它键窗口；代价是按下事件晚约 40 ms、抬起晚约 120 ms |
| 上拉 | 必须用外部 10k；内部上拉约 45 kΩ，三档会挤到 0–154 mV 并随温漂重叠 |

真机证据（2026-11-06，上一项目）：三键各按一次，上报 `UP / DOWN / OK` 计数 4/1/4；15 个手势码（3 键 × press/click/double/long/release）15/15。

**边界**：只验了分类结果，**没有用万用表复核实际电压**，电阻误差与温漂窗口也未测。换板或自定阈值前必须重新标定。

**分级（2026-11-14 决策）**：MicClicker 在**同一块板**上复用 BSP 窗口、不自定阈值，万用表复核**不是编码前置**。分类判定依据是芯片 ADC 读数而非引脚绝对电压，因此由 C3 最小固件记录各键态 ADC 原始读数（分布、噪声、离窗口边界的裕量）即可复核，且比万用表更贴近判定逻辑（见第 10 节第 2 步）。只有换板、自定阈值或实测出现误分类时，才需要独立电表交叉验证。

**本轮复核结果（2026-11-14，Curve Fitting 已启用）**：最终探针等待目标键态连续出现 3 次后才采集 400 个样本，避免用户提示延迟与采样窗口错位。

| 键态 | raw min–max | raw 均值 | raw 标准差 | 校准 mV min–max | 窗口裕量 | 误分类 |
| :--- | ---: | ---: | ---: | ---: | :--- | ---: |
| RELEASED | 4095–4095 | 4095.000 | 0.000 | 2918–2918 | 距 OK 上界 1018 mV | 0/400 |
| UP | 1–6 | 3.660 | 0.905 | 0–5 | 上界 145 mV | 0/400 |
| DOWN | 394–410 | 402.760 | 4.153 | 295–307 | 下界 145 / 上界 140 mV | 0/400 |
| OK | 794–810 | 803.185 | 4.153 | 592–603 | 下界 145 / 上界 1297 mV | 0/400 |

这些结果支持当前分类算法和既有窗口在本板、本次射频条件下可用，不等于独立万用表精度验证。松开态 raw 已到 4095，校准值为 2918 mV，不把它解释成实际 3.3 V 供电的精确测量。

**bootloader 阶段没有 ADC**：三键按下时都在数字低电平区（C3 的 VIL≈0.83 V），所以「按住任意功能键 5 s 进恢复」对三个键都成立——不能写成「只按 UP」。但本设备没有 recovery 分区，MicClicker 已决定不采用该应用恢复入口，见第 13.5 节。

## 8. MicClicker 新增的验证项

上一项目只用 NimBLE BLE，**固件从未初始化 Wi-Fi**；编码用的是 IMA-ADPCM，不是 G.722。下面这些**没有被任何既有记录覆盖**：

1. **Wi-Fi / ESP-NOW**：Wi-Fi 初始化与 STA 扫描**已通过（2026-11-14）**；ESP-NOW 单播/广播、加密单播、250 字节包、丢包与重传、距离与穿墙仍未验证。ESP-NOW 与 BLE 共用 2.4 GHz 射频和天线；本项目不用 BLE，但同板共存与发射功率仍要测。
2. **G.722 在 C3 上的开销**：编码耗时、RAM 占用、20 ms 周期能否稳住。这是 CPU 侧的新负载，旧项目没有数据。
3. **漂移链路重算**：旧项目是「C3 时钟 ↔ Mac 主机时钟」；新链路是「C3 采样时钟 ↔ S3 ↔ USB 主机时钟」。0.42% 的量级可作参考，补偿点必须重新设计。
4. **功耗**：ESP-NOW 要求射频常开，比 BLE 更耗电；又因射频无法关闭而无法深度休眠，续航只能靠实测。500 mAh 电池的可用时长目前完全未知。
5. **配对输入**：**方案已确认（2026-11-14）**：全键松开时 DOWN 长按 5 秒进入 30 秒配对窗；DOWN 首版保留，不与默认 HID 映射冲突。ADC 电阻梯不假定可靠组合键，解除绑定由配置工具发起并用 DOWN 物理确认；不采用「长按 5 秒进 recovery」。
6. **调试口**：UART0 TX 与背光冲突，只能使用 USB-Serial-JTAG 当控制台。**已在 Wi-Fi 扫描及 ADC 采样期间实测日志连续可读（2026-11-14）**；更长时间和 ESP-NOW 负载下稳定性仍需后续观察。
7. **状态指示**：没有可控 LED（上游 BSP 也没有 LED 接口）；背光可做被动提示（旧项目用它做低电量短闪），充电灯只能人眼看。

## 9. 烧写与备份前置

### 9.1 该设备的实际分区表（2026-11-14 实测）

**这块板当前不是平台模板**，只有 `nvs` + `phy_init` + `factory(0x7F0000)` 三项，详见第 13.5 节。

| 区域 | 偏移 | 大小 | 处置 |
| :--- | :--- | :--- | :--- |
| bootloader | `0x0` | 20 992 B | 写 |
| 分区表 | `0x8000` | `0x1000` | 写（改布局时） |
| nvs | `0x9000` | `0x6000` | **不写**（含 RF 校准 `phy` 与 BLE 绑定 `nimble_bond`） |
| phy_init | `0xF000` | `0x1000` | 不写（当前全 `0xFF`） |
| factory app | `0x10000` | `0x7F0000`（8128 KB 上限） | 写 |

这里的“不写”指烧录命令不覆盖 NVS/`phy_init`，不代表运行中的 Wi-Fi 驱动完全只读。2026-11-14 首次初始化 Wi-Fi 时出现 `Saving new calibration data`；只读回查确认 NVS 摘要变化，但 `phy`、校准、`nimble_bond`、`local_irk` 条目名和数量仍在。BLE 重连未重新验证，详见第 14 节。

### 9.2 平台模板（上一项目的计划值，**本设备尚未采用**）

| 区域 | 偏移 | 大小 | 处置 |
| :--- | :--- | :--- | :--- |
| bootloader | `0x0` | | 写 |
| 分区表 | `0x8000` | | 写 |
| nvs | `0x9000` | `0x6000` | 不写（用户配置） |
| phy_init | `0xF000` | `0x1000` | 不写（RF 校准） |
| factory app | `0x10000` | 3 MB 上限 | 写 |
| cardid（设备身份） | `0x356000` | `0x4000` | **绝不写**（出厂预置） |
| recovery（永久恢复镜像） | `0x700000` | `0x100000` | **绝不写**（出厂预置） |

切换到该模板的代价：`factory` 上限从 8128 KB 缩到 3 MB，且会覆盖 `0x356000` 附近的裸区域。**这是需要显式决定的变更**，不是「沿用现状」。

注意：

- **先整片备份**：`read_flash 0x0 0x800000`。**已实测（2026-11-14）**：460800 下用时 184.1 s、364.5 kbit/s，比 S3 走 CH343（约 13 s/MB）慢约 2.7 倍；备份后核对 sha256（见第 13.2 节）。备份是一次性产物，按 AGENTS.md 放 `.tmp/`，不进仓库。
- **不要用 merged bin 从 `0x0` 整段写**：`idf.py merge-bin` 会用 `0xFF` 填满空隙，把 nvs 和 phy_init 一起抹掉（上一项目踩过，表现是「插上 USB 就掉配对」）。要按上表切片写。
- **按 label 找分区，不要按 type/subtype**：如果将来采用 9.2 的模板，`cardid` 的 subtype 与 `nvs` 相同（都是 `data/nvs`），按类型找会把 nvs 定位到 `0x356000`。
- **分区表布局已明确决定（2026-11-14）**：继续使用本设备实测的 `factory=0x7F0000` 三项布局，不切换到 9.2 的平台模板，也不把裸区域解释为 `cardid` / `recovery`。
- **同一块板只能跑一套固件**：刷 MicClicker 的 ESP-NOW 固件会覆盖上一项目的 BLE 固件。要两边都能用，得准备第二块板。
- **开机态检查**：关机时插 USB 只给充电 IC 上电（绿灯亮、C3 电源轨断开），串口和射频都不出现。先按电源键 0.5 s，再看绿灯，最后才怀疑线材；线必须是数据线。
- **下载模式不用按键**：C3 的 USB-Serial-JTAG 是芯片内置（不是 CH340/CP2102），esptool 可走 USB 控制线软复位进 ROM 下载态，不用按 BOOT。这也是上一项目「裸片首烧」路线的前提。

### 13.4 两个需要说明的发现

**发现一：板上固件不是上一项目最后一次构建的产物。**

`device/build/ai-passport-mic.bin`（2026-11-10，725 232 B，sha256 `39dc1823…`）与板上 707 328 B 不一致。板上这版构建于 **Nov 6 08:32:55**，与项目记录的 `0.1.0` 早期版本对应。也就是说 2026-11-06 之后那些改动（省电两档、屏幕、遥测等）**没有烧进这台设备**。旧项目文档里「已真机验证」的条目，凡是在 11-06 之后完成的，都不能认为在这台板子上成立。

**发现二：0xBD000 起的残留区来源未确认。**

该段 3.05 MB 连续非空，熵接近随机，无 `ESP-IDF`/`v5.`/`folotoy` 等版本标识，也没有第二个 app 描述符（全片只有 `0x10020` 一处 magic）。扫描到 `Aug 25 2025` 一处、中文串 93 条（内容为 Wi-Fi 配网引导文案，如「正在找附近的网络」「连上家里的」），以及 23 处 `ssid`、34 处 `wifi`。倾向判断是**上一轮器件擦除后残留的旧固件/资源**（写 app 只写了 690 KB，未覆盖其后内容），但现有证据不足以确认来源，**按「未知内容」对待**，不要引用其数据。

**与发现一相关：MAC 与上一项目记录完全相同。**

`98:c3:77:f6:c6:44` 同时是 USB 序列号，与 `ai-passport-mic` 项目文档记录的值一致，**基本可确认是同一块物理板卡**，不是两地两台。这与发现一吻合：这块板停在 `Nov 6 08:32:55` 那版固件，之后没有再烧过。

由此需要复核一件事：上一项目文档里标注「2026-11-08 真机验证通过」的条目（屏幕初始化、自动熄屏、屏幕标签下发）**晚于板上固件的构建时间**。如果这段时间确实没重烧设备，那些结论对应的固件状态与本板当前状态不一致。在弄清楚之前，**这些「已验」条目不应直接当作本项目的既有硬件结论使用**；至少屏幕与遥测相关部分要重新确认。

### 13.5 分区表与平台模板不符（重要）

实测分区表只有 3 项：

| Name | Type | SubType | Offset | Size |
| :--- | :--- | :--- | :--- | :--- |
| `nvs` | `0x01` | `0x02` | `0x009000` | `0x006000` |
| `phy_init` | `0x01` | `0x01` | `0x00f000` | `0x001000` |
| `factory` | `0x00` | `0x00` | `0x010000` | **`0x7F0000`（8128 KB）** |

**没有 `cardid@0x356000`，也没有 `recovery@0x700000`。** 这与上一项目 `device/partitions.csv` 的平台模板（`factory` 收 3 MB + `cardid` + `recovery`）不一致，也与本文 9.2 节抄录的模板表不一致。

对照上一项目 git 历史：`21bd96e`（2026-11-05）首次引入的 `partitions.csv` 正是这三项、`factory` 为 `0x7f0000`；平台模板（`0x300000` + `cardid` + `recovery`）是**工作区未提交改动**，从未构建进这台设备。

因此：

- **本文 9.2 节的平台模板把这设备说得太理想**，`cardid` / `recovery` 两个区在它上面**根本没有被声明**。`0x356000` 处的 16 KB 非空数据（`0x700000` 处全 `0xFF`）是裸区域内容，不是受保护的身份分区。
- 上一项目文档里「平台模板 + 恢复入口」那段描述属于**未落地的计划**，不是这设备的当前状态。
- 要不要改用平台模板，是**未来要显式决定的事**，不是「沿用现状」。一旦切换，`factory` 从 8128 KB 缩到 3 MB，且会覆盖 `0x356000` 附近区域。

### 13.6 烧写影响提示

- 整片备份已完成，任何后续写入都可回滚到本文件记录的 sha256。
- **不要把 merged bin 从 `0x0` 整段写**：会用 `0xFF` 填满空隙，把 NVS（含 RF 校准与 BLE 绑定）一起抹掉。要按分区切片写。
- NVS 里已有 BLE 绑定数据；烧录命令没有覆盖 NVS，但 Wi-Fi 初始化可能按驱动规则重校准并改写 `phy`。若还要恢复上一项目的 BLE 固件，整片抹除后需重新配对；本轮未做 BLE 重连验证。
- 安全启动与 Flash 加密均未启用，可自由烧写；这也意味着 ROM 下载态始终可用，不存在刷坏报废。

## 14. MicClicker Wi-Fi 与 ADC 自检（2026-11-14）

目标设备再次核对为 ESP32-C3 rev v1.1、8 MB XMC Flash、MAC `98:c3:77:f6:c6:44`，端口 `/dev/cu.usbmodem11301`。完整烧录只写 `0x0`、`0x8000`、`0x10000` 三段；探针调整只用 `app-flash` 更新 factory，未使用 merged-bin 或整片擦除。

```bash
./firmware/build.sh c3
export IDF_PYTHON_ENV_PATH="$HOME/.espressif/python_env/idf5.5_py3.13_env"
source ~/esp/esp-idf-v5.5.3/export.sh
idf.py -C firmware/c3 -p /dev/cu.usbmodem11301 -b 460800 flash
idf.py -C firmware/c3 -p /dev/cu.usbmodem11301 -b 460800 app-flash  # 后续仅更新应用时使用
idf.py -C firmware/c3 -p /dev/cu.usbmodem11301 monitor -b 115200
```

最终有效轮次为 `.tmp/c3-selftest-20261114-153944/monitor.log`：Wi-Fi 扫到 18 AP，最强 RSSI −49 dBm；ADC Curve Fitting 可用，四键态均 400/400 且 0 误分类，末尾为 `SELFTEST: PASS wifi=1 adc=1`。详细分布见第 4 节。该轮采用目标键态连续出现 3 次后采集 400 样本的触发逻辑；仓库修正版另增加 60 秒等待超时，构建证据为 `.tmp/c3-selftest-20261114-160647/build.log`。

较早两轮使用固定准备窗口，因用户提示与按键时序错位而出现非目标键态样本；这些轮次只判为流程无效，**不作为按键硬件失败证据**，也不用于第 4 节统计。工程随后改为触发式采样并重新取得上述有效轮次。

### NVS 影响复核

首次 Wi-Fi 初始化日志出现 `Saving new calibration data due to checksum failure or outdated calibration data`。因此“烧录不写 NVS”不能扩展成“运行 Wi-Fi 后 NVS 完全不变”。2026-11-14 只读回 `0x9000–0xF000`（24 KB）到 `.tmp/c3-selftest-20261114-155526/nvs-after.bin`，与备份相比摘要不同；但 `phy`、`cal_data`、`cal_version`、`cal_mac`、`nimble_bond`、`local_irk` 的名称及出现次数保持一致。这里只核对条目名，不报告秘密值，也不据此宣称 BLE 重连已经通过。
