# ESP-NOW 无线分测

第 3 阶段（`docs/DESIGN.md` 第 6 节）要求「用合成数据测试 ESP-NOW 丢包、乱序、吞吐、配对和心跳」。本目录是这个验证的入口：主机侧协议测试不需要硬件，真机探针需要两块板。

## 结论与边界（先说不能证明什么）

2026-11-14 实测，C3 `98:c3:77:f6:c6:44` → S3 `c4:9e:7e:3c:d5:d4`，信道 1，两块板相距约 1 米、无遮挡。

| 项目 | 状态 |
| :--- | :--- |
| 主机侧协议编解码（长度、版本、字节序、序号规则） | **已通过**：141 项断言 |
| 丢包（合成流量，连续 3 轮 + 最终轮） | **已通过**：1422/1422、1312/1312、1311/1311 等，**0 丢包** |
| 乱序 / 迟到帧判定 | **已通过**：主机侧覆盖；真机未观测到乱序（ESP-NOW 不重排） |
| 重复帧去重（按键重传） | **已通过**：20 个事件全部应用，40 次重传全部抑制 |
| 吞吐 | **实测 406–507 kbit/s 空口**（3.5 s 突发，1061–1172 帧） |
| 心跳 RTT | **实测 2.6–12.3 ms**（平均 5.7–8.2 ms，信道 1，1 米） |
| 配对 + 加密单播 | **已通过**：配对成功、加密心跳往返成功、绑定写入 NVS |
| 绑定持久化（重启后仍存在） | **部分**：写入成功且下次启动能读出；**重启后自动用旧绑定重连的路径未实现** |
| 配对过程的机密性（防中间人） | **未实现**：配对请求是明文，见 `docs/protocol.md` 3.5 节 |
| 距离、穿墙、干扰、多信道 | **未测**：只测了 1 米直视、信道 1 |
| 与音频全链路并发（C3 采集 + S3 USB 输出） | **未测**：属于第 4 阶段 |

**不要把本页当作"无线已全部验证"**：测的是合成流量在 1 米直视下的丢包、吞吐、配对和心跳，不是语音链路可用性、传输距离或抗干扰能力。

## 两层验证

### 1. 主机侧协议测试（无需硬件）

```bash
./firmware/tests/link_proto/run.sh
```

用主机 `cc` 编译**固件同一份** `firmware/components/link_proto/src/mic_link.c`，覆盖：

- 逐字节的空口布局（小端、版本、类型、精确长度）；
- 拒绝规则：短头、未知版本、未知类型、截断、多余尾字节、类型与长度不匹配；
- 序号：顺序、缺口、迟到补齐、重复、回绕、跨越回绕的缺口、超窗口跳变；
- 会话切换重置跟踪；
- 按键重传契约（重传字节完全相同，ACK 回送事件序号而非自身序号）。

`hostshim/` 复用 `firmware/tests/g722/hostshim/esp_err.h`，只是让组件在没有 IDF 的主机上编译通过。

### 2. 真机探针（需要两块板）

探针是独立构建配置，不是运行时开关：C3 上它替换交互式自检，S3 上它替换 USB 复合设备，因此产物里不会同时存在相互争用外设的两套逻辑。

```bash
./firmware/build.sh c3 --probe    # 发送端
./firmware/build.sh s3 --probe    # 接收端
```

恢复产品配置用 `./firmware/build.sh c3`（自检）或 `./firmware/build.sh s3`（USB 原型）。

烧录按 `firmware/README.md` 的检查流程执行，只写 `0x0`、`0x8000`、`0x10000` 三段。两端烧录后**同时复位**，固件会等 8 秒再开始，给主机留出打开两个控制台的时间。

#### 捕获与判分

两端都需分别打开控制台并保存日志（C3 用 `/dev/cu.usbmodem11301`，S3 用 `/dev/cu.usbmodem5D4D0449961`，波特率 115200）。随后：

```bash
./firmware/tests/espnow/check.sh <sender-log> <receiver-log>
```

脚本按 `docs/protocol.md` 的判据给出 `ESPNOW_PROBE: PASS` 或 FAIL，并逐条打印依据。它只读日志，不接触硬件。

#### 探针阶段

| 阶段 | 内容 | 判据 |
| :--- | :--- | :--- |
| `discovery` | 广播心跳找接收端 | 收到回复，拿到对端 MAC |
| `audio_stream` | 3 s 满速突发（约 3.5 s 实际） | 0 丢包、0 重复、吞吐记录 |
| `audio_spaced` | 250 帧按 20 ms 节奏 | 0 丢包，RTT 统计 |
| `key_retry` | 20 个事件，每个发 3 次（同序号） | 应用 20，抑制 40 |
| 配对 | 广播 PAIR_REQ，切换加密单播 | `result=ok encrypt=1`、`persistence=ok` |
| `encrypted` | 加密心跳往返 | 收到加密回复 |

`audio_stream` 阶段的 `tx_immediate_errors` 非零是**预期现象**：满速发送会持续撞上驱动队列上限（`ESP_ERR_ESPNOW_NO_MEM`），探针退避并复用同一序号重试，所以它既不是丢包也不计入序号缺口。真实信道丢包看接收端累计 `audio_gap - audio_late`。

## 实测中修正的问题

这些是探针和组件的真实缺陷，不是无线质量问题。逐条记录，因为都会重复出现（协议层摘要见 `docs/protocol.md` 第 7 节）。

1. **广播发不出去**：ESP-NOW 要求目标地址已登记为 peer，广播也不例外，否则 `esp_now_send` 返回 `ESP_ERR_ESPNOW_NOT_FOUND`。首轮 24 次广播全部立即失败。
2. **接收端回不了包**：只登记了发送端到接收端的方向。接收端必须先登记发送端地址才能回心跳回复。
3. **发送失败仍推进序号**：背压时前进 `seq` 制造了 **2998 个假缺口**。改为只有发送成功才推进后，丢包归零。
4. **按到达顺序匹配 ACK**：收尾等待被上一阶段的残留回复满足，报出「接收端应用了 0 个按键事件」（实际 20 个）。改为按 `echo_seq` 匹配。
5. **突发期收尾心跳被丢**：链路饱和时接收端控制路径排队，单次收尾心跳会丢，阶段丢包数字因此不可读。改为重试收尾。
6. **探针读不到 READY 行**：`PROBE_READY` 在 8 秒启动延时之前打印，主机打开控制台时已经滚过去。把会话号与信道重复到 `PROBE_ARMED` 行。

## 尚未做的部分

- **重启后自动按旧绑定重连**：绑定能写入、能读出，但"开机读取绑定 → 直接加密单播 → 不重新配对"这条路径未实现，属于第 5 阶段的故障恢复工作。
- **配对过程防中间人**：明文交接是当前实现的已知限制，需要带外确认或 ECDH 才能消除。
- **距离、穿墙、干扰**：本页数字只描述 1 米直视、信道 1 的条件。
- **与音频并发**：探针用合成模式替代麦克风，没有与 G.722 编码、USB 输出同时运行。并发下的丢包与延迟属于第 4 阶段。
